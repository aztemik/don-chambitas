## Objetivo

Conectar P-02 y P-03 con `RepositorioAuth` mediante ViewModels inyectados por
Hilt, y dejar preparado el estado y ViewModel de P-04 para S2-T10. Los estados
de UI reactivos representan captura, carga, éxito y error, sustituyendo el
estado local y la navegación provisional donde las pantallas ya existen.

La implementación usa exclusivamente la interfaz `RepositorioAuth` y su
enlace falso actual. No consume Supabase ni código exclusivo de S2-T04.

## Contexto

S2-T02 y S2-T03 dejaron las pantallas y sus estados con lógica local temporal.
S1-T13 ya aporta `RepositorioAuth`, `RepositorioAuthFalso` y su enlace en Hilt.
Esta tarea mueve la coordinación asíncrona a dos ViewModels y conserva los
contenidos visuales puros para previews y pruebas de Compose.

S2-T04 está en revisión en otro pull request. Por eso este ticket no añade ni
duplica sus funciones de validación, no depende de ellas y debe poder partir de
`main`. Cuando ambos cambios se integren, S2-T04 seguirá siendo la única dueña
de las reglas de formato y validación por campo.

## Qué hacer

Crear `IniciarSesionViewModel`, `RegistroViewModel` y
`RecuperarContrasenaViewModel` como `@HiltViewModel`, con `RepositorioAuth`
recibido por constructor y un `StateFlow` de solo lectura.
Cada evento de captura actualiza una copia inmutable del estado y limpia el
error general anterior. Los límites de captura y el filtrado numérico del
teléfono permanecen donde ya estaban, pero pasan a ejecutarse desde el
ViewModel de registro.

Al enviar, normalizar el correo con `trim().lowercase()` y los nombres con
`trim()`. Mientras espera al repositorio, publicar `cargando = true`, conservar
lo escrito, limpiar el error general y bloquear envíos simultáneos. En éxito,
publicar un destino de un solo uso según el rol de la sesión: P-05 para cliente
y P-10 para trabajador. Tras un registro exitoso se consulta `sesionActual()`;
si excepcionalmente no hay sesión, el destino es P-02. La pantalla consume el
destino y lo limpia antes de delegar la navegación al grafo.

En error, conservar todos los valores capturados, terminar la carga y publicar
el `TipoError`. En el registro, conservar además el mensaje del repositorio
solo para `VALIDACION`, porque puede explicar un correo duplicado. El reintento
repite la última operación con los valores actuales. No se traducen ni se
inventan errores de backend.

P-04 conserva el correo, llama a `recuperarContrasena` normalizado y cambia a
la vista de confirmación en cualquier éxito. En error conserva el formulario,
expone el tipo y permite reintentar solo los tipos reintentables. Su pantalla no
se implementa ni se conecta al grafo: corresponde a S2-T10.

P-03 conserva la exigencia de elegir un rol que ya pertenece a S2-T02. Las
demás validaciones de formato, pérdida de foco y foco al primer inválido siguen
fuera de esta rama porque pertenecen a S2-T04.

En `GrafoNavegacion`, sincronizar el marcador temporal que todavía usan las
guardas con el destino emitido tras una respuesta exitosa del repositorio.
S2-T15 reemplazará ese marcador por la sesión real. La fuente activa continúa
siendo `RepositorioAuthFalso`; ninguna pantalla conoce su implementación.

## Criterios de aceptación

- [x] Los tres ViewModels reciben únicamente `RepositorioAuth`, nunca una implementación concreta
- [x] Los tres exponen estado inmutable mediante `StateFlow`
- [x] Los eventos de captura actualizan el estado sin lógica de repositorio en los Composables
- [x] El correo se envía con `trim().lowercase()` y los nombres con `trim()`
- [x] P-03 conserva límites de captura y teléfono exclusivamente numérico de diez posiciones
- [x] Durante cada operación `cargando` es verdadero, los controles quedan bloqueados y no hay doble envío
- [x] Un éxito de inicio de sesión navega según el rol de la `Sesion` devuelta
- [x] Un registro exitoso consulta `sesionActual()` y navega según su rol
- [x] Un registro exitoso sin sesión vuelve a P-02
- [x] Una recuperación exitosa cambia a la vista de confirmación sin revelar si el correo existe
- [x] El destino se consume una sola vez y no vuelve a navegar tras recomposición
- [x] Un error conserva lo escrito y expone su `TipoError`
- [x] P-02 muestra el mensaje específico de credenciales rechazadas para `AUTENTICACION`
- [x] P-03 muestra el mensaje del repositorio cuando el error es `VALIDACION`
- [x] Los errores reintentables pueden repetir la operación
- [x] P-03 no llama al repositorio mientras no haya rol seleccionado
- [x] Cero llamadas directas a `RepositorioAuth`, Supabase o fuentes concretas desde los contenidos visuales
- [x] No se copia ni se depende de código exclusivo de S2-T04
- [x] `LIMITE_IA`, si llega a autenticación, se presenta como `DESCONOCIDO`
- [x] Los ViewModels tienen pruebas unitarias de éxito, error, carga, normalización, reintento y consumo del destino o confirmación
- [x] Las pruebas instrumentadas existentes siguen pasando con la integración de los ViewModels
- [x] `./gradlew assembleDebug` compila
- [x] `./gradlew testDebugUnitTest` pasa
- [x] `./gradlew connectedDebugAndroidTest` pasa en Pixel 10
- [x] Probada a mano en Pixel 10 con alta e inicio de sesión contra `RepositorioAuthFalso`

## Cómo probarlo

```bash
./gradlew assembleDebug testDebugUnitTest connectedDebugAndroidTest
```

En Pixel 10:

1. Abre P-03, elige un rol y completa los datos; durante el alta el botón debe
   mostrar carga y, al terminar, debe abrir el inicio correspondiente al rol.
2. Regresa a la aplicación desde cero e inicia sesión con el correo creado; la
   pantalla debe mostrar carga y navegar al mismo rol.
3. Intenta iniciar sesión con un correo inexistente: se conserva lo escrito y
   aparece "Correo o contraseña incorrectos" sin navegar.
4. Registra dos veces el mismo correo: se conserva el formulario y aparece el
   mensaje de correo ya registrado.
5. Fuerza, mediante pruebas unitarias, errores de red, servidor y desconocido;
   el reintento debe repetir la operación y no duplicarla mientras carga.
